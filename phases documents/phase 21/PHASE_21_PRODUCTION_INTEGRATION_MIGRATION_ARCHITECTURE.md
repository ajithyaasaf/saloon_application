# PHASE 21 — PRODUCTION INTEGRATION & CONSUMER MIGRATION ARCHITECTURE BLUEPRINT

**Status**: COMPLETED, VERIFIED & FROZEN  
**Module**: Phase 21 — Production Integration & Consumer Migration  
**Scope**: Codebase audit, legacy Cloudinary SDK removal, transition to Phase 20 File & Media Engine, configuration hardening, non-breaking schema compatibility, and end-to-end regression validation  
**Target Platform**: `@saloon/api` (NestJS / TypeScript / Prisma / PostgreSQL / Cloudflare R2 / AWS S3)

---

## 1. Purpose & Objectives

Phase 21 bridges the gap between the standalone implementation of Phase 20 (File & Media Storage Engine) and the broader backend application. Prior to Phase 21, the `UsersService` avatar upload logic directly called the third-party Cloudinary SDK, bypassing the enterprise storage engine, access control layers, audit trails, and multi-provider abstractions created in Phase 20.

The key objectives of Phase 21 were:
1. **Eliminate Raw Storage SDK Leakage**: Remove direct dependencies on third-party cloud SDKs (e.g. `cloudinary` v2) from business domain services.
2. **Standardize on Phase 20 Engine**: Route all binary and media asset handling through `IStorageProvider` and Phase 20 services (`FileUploadService`, `FileAccessService`).
3. **Preserve Non-Breaking Compatibility (Option B Pattern)**: Maintain existing database relationships (`User.avatarMediaId` referencing `Media.id`) without forcing disruptive schema migrations, populating the `Media` record with URLs generated by Phase 20.
4. **Environment Hardening**: Make legacy Cloudinary environment variables optional and remove `CLOUDINARY` from the active storage provider enum list.
5. **Zero Regression**: Ensure all 245+ test suites (1,678+ tests) across the monorepo pass cleanly.

## 2. Architectural Analysis & Strategy Decision

### Pre-Migration State
```
[Client] ──> UsersController.uploadAvatar()
                    │
                    ▼
              UsersService ──────(Direct Cloudinary SDK)──────> [Cloudinary API]
                    │
                    ▼
             UserRepository ───> [PostgreSQL: media table]
```

### Post-Migration Architecture (Phase 21 Target)
```
[Client] ──> UsersController.uploadAvatar()
                    │
                    ▼
              UsersService ───> [IStorageProvider] (Injected via STORAGE_PROVIDER_TOKEN)
                    │                │
                    │                ├──> [Local Storage Adapter] (Dev/Test)
                    │                └──> [Cloudflare R2 / AWS S3] (Prod)
                    │
                    ├───> FileAccessService (Resolve access URL)
                    │
                    ▼
             UserRepository ───> [PostgreSQL: media table & User.avatarMediaId]
```

### Schema Strategy Decision
- **Option A (Disruptive)**: Add `avatarFileAssetId` column on `User` model, migrate existing foreign keys, and drop legacy `Media` dependencies. Required a Prisma migration and dual-read fallback logic.
- **Option B (Non-Breaking / Selected)**: Inject `IStorageProvider` directly into `UsersService`. Upload buffer to the configured storage provider (R2/S3/Local), retrieve access URL via `FileAccessService`, and write the resulting asset URL to the existing `Media` record.
- **Verdict**: Option B was selected and executed to maintain 100% backward compatibility with zero database downtime or breaking API changes.

## 3. Comprehensive File Audit & Changes

### 3.1 Domain Services Migration
#### `apps/api/src/domains/users/users.service.ts`
- **Removed**: `import { v2 as cloudinary, UploadApiResponse } from 'cloudinary'`
- **Injected**:
  - `@Inject(STORAGE_PROVIDER_TOKEN) private readonly storageProvider: IStorageProvider`
  - `private readonly fileAccessService: FileAccessService`
- **Refactored**: `requestAvatarUpload()` buffer handling to call `this.storageProvider.uploadBuffer()` with standardized object key path: `users/{userId}/avatars/{hash}.{ext}`.
- **Preserved**: Distributed lock idempotency via Redis (`setNX` / `del`) preventing concurrent avatar upload races.

#### `apps/api/src/domains/users/users.module.ts`
- **Imported**: `MediaModule` to enable dependency injection of `FileAccessService` and `STORAGE_PROVIDER_TOKEN`.

### 3.2 Configuration & Environment Hardening
#### `apps/api/src/config/config.validation.ts`
- Marked `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` as `.optional()`.
- Updated `STORAGE_PROVIDER` Joi validation enum to `Joi.string().valid('LOCAL', 'R2', 'S3').default('LOCAL')`.

#### `apps/api/src/config/configs.ts`
- Documented Cloudinary configuration block as deprecated/optional.

### 3.3 DTO & Swagger Modernization
#### `apps/api/src/domains/users/dto/avatar.dto.ts` & `user-profile.dto.ts`
- Updated API operation and property descriptions, replacing legacy "Cloudinary CDN" references with "Storage Engine CDN" provider-neutral phrasing.

## 5. Architectural Invariants Enforced

1. **No Raw SDK Imports in Domain Modules**: All file uploads must route through `IStorageProvider` or `FileUploadService`.
2. **Provider Swappability**: Switching between `LOCAL`, `R2`, and `S3` requires only an environment variable change (`STORAGE_PROVIDER`), without any code changes.
3. **Multi-Tenant Isolation**: Tenant boundaries are preserved across physical storage object keys and database records.
